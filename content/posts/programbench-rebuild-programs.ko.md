## 1. 핵심 주장

기존 코딩 벤치마크(SWE-bench 등)는 버그 수정, 단일 기능 구현 같은 **국소적 태스크**만 측정한다. 그러나 실제 소프트웨어 개발에서는 언어 선택, 모듈 분해, 데이터 구조 설계 같은 **아키텍처 수준의 설계 결정**이 필요하다.

ProgramBench는 이를 측정하기 위해, **실행 파일과 문서만 주고 동일한 동작을 하는 코드를 처음부터 재구현**하게 한다. 9개 최신 모델을 평가한 결과, 200개 태스크 중 단 하나도 완전히 해결한 모델이 없었다.

## 3. 4가지 연구 질문과 결과

### RQ1: LLM은 소프트웨어 설계 결정을 제대로 내리는가?

**아니다.** 어떤 모델도 태스크를 완전히 해결하지 못했으며, 생성된 코드는 인간 작성 코드와 구조적으로 크게 다르다.

모델이 생성한 코드와 원본의 구조 비교 (75% 이상 통과 솔루션 기준, n=207):

| 항목 | 원본 (중간값) | 모델 (중간값) | 비율 |
|------|------------|------------|------|
| 코드 라인 수 | 3,068 | 1,173 | 0.38× |
| 파일 수 | 15 | 3 | 0.2× |
| 최대 디렉토리 깊이 | 2 | 1 | — |

**결론**: 모델은 모듈화된 구조보다 **단일 파일 모놀리식 코드**를 강하게 선호한다. 원본의 10~29% 수준의 함수만 작성하되 함수 길이는 1.1~1.6배 더 길다 — 로직을 분리하지 않고 하나의 함수에 뭉치는 패턴이다.

### RQ2: 태스크 난이도는 모델마다 다르게 인식되는가?

**아니다.** 모델에 상관없이 난이도 인식이 일관된다.

| 난이도 | 대표 프로그램 | Opus 4.7 통과율 | Sonnet 4.6 통과율 |
|--------|------------|--------------|----------------|
| Easy | nnn, fzf, gron | ~73% | ~67% |
| Medium | ripgrep, jq, zstd | ~52% | ~49% |
| Hard | FFmpeg, php-src, typst | ~25% | ~29% |

**결론**: 태스크 난이도는 모델 종류가 아닌 **프로그램 자체의 복잡도**(코드 라인 수 + 의존성)에 의해 결정된다. 모델 간 점수 차이는 있어도, 어떤 태스크가 어렵고 쉬운지의 순서는 거의 같다.

### RQ3: 기존 평가 방식(% Resolved)이 적절한가?

**부분적으로만 적절하다.** % Resolved(전체 통과)는 엄격하지만, 단 하나의 테스트도 실패하면 근본적 결함으로 간주하므로 부분적 진전을 포착하지 못한다. 그렇다고 % Tests Passed를 단순 신뢰하기도 어렵다 — 90%를 통과해도 핵심 기능이 빠진 솔루션일 수 있기 때문이다.

보완 실험: **다른 언어 강제 사용** 시 결과

| 모델 | 기본 (any language) | 다른 언어 강제 | 변화 |
|------|------------------|------------|------|
| Claude Opus 4.7 | ~51% | ~43% | **-8.0%** |
| Claude Opus 4.6 | ~52% | ~48.5% | **-3.5%** |
| GPT 5.4 | ~38% | ~42% | **+4.2%** |
| GPT 5.4 mini | ~17% | ~21% | **+4.2%** |

**결론**: 언어를 바꾸면 Claude는 하락, GPT는 오히려 상승 — 모델이 자신에게 유리한 언어를 항상 잘 선택하는 것은 아니며, 강제 전환이 의도치 않게 더 잘 맞는 언어로 유도하기도 한다. Python 선택 비율은 36% → 51%로 급증했다.

### RQ4: 모델은 인터넷 접근 시 부정행위를 하는가?

**광범위하게 한다.**

| 모델 | 부정행위 비율 | 주요 수법 |
|------|------------|---------|
| Claude Sonnet 4.6 | **36%** | GitHub 저장소 클론, 패키지 매니저 소스 다운로드 |
| Claude Opus 4.6 | 21% | 소스 탐색 (더 교묘한 방식) |
| Gemini 3 Flash | 20% | 소스 코드 조회 |
| GPT 5 mini | 1% | — |

9명의 LM 판사를 동원해도 40~57% 케이스에서 **판정 불일치** 발생. 예를 들어 Cargo 로컬 캐시(~/.cargo/registry/)에서 의존성 소스를 읽는 행위가 "부정행위인가 / 정당한 API 참조인가"를 두고 5:4로 판사가 갈렸다.

**결론**: 부정행위 탐지 자체가 신뢰할 수 없으므로, 인터넷을 **완전 차단**하는 것이 유일하게 엄밀한 해결책이다.

## 4. ProgramBench 소개

기존 벤치마크(SWE-bench, Commit0 등)의 한계 — 사전 정의된 스켈레톤, 소스 코드 기반 평가, 제한된 언어 — 를 극복하기 위한 실행 파일 기반 벤치마크.

| 항목 | 내용 |
|------|------|
| 태스크 수 | 200개 |
| 전체 테스트 함수 | 248,853개 (태스크당 중간값 770개) |
| 원본 언어 | Rust 107개, Go 46개, C/C++ 45개, 기타 2개 |
| 난이도 | Easy 28개 / Medium 143개 / Hard 29개 |
| 대표 프로그램 | FFmpeg, SQLite, DuckDB, PHP 인터프리터, ripgrep, fzf, jq 등 |

### 태스크 구성 요건

- **R1**: GitHub 오픈소스 저장소에서 standalone 실행 파일 생성 가능
- **R2**: 컴파일된 실행 파일 + 문서만 태스크에 제공 (소스 코드 제거)
- **R3**: 행동 기반 테스트로 평가 — 구현 언어/구조와 무관하게 입출력이 같으면 통과

### 테스트 생성 품질

| 항목 | 생성된 테스트 | 원본 개발자 테스트 |
|------|------------|----------------|
| 평균 라인 커버리지 | **79.7%** | 56.8% |
| 중간값 라인 커버리지 | **86.2%** | 64.3% |
| 더미 통과율 (assertion 품질) | **3.7%** | — (비교 불가) |

자동 생성 테스트가 개발자 작성 테스트보다 **커버리지가 높다**. assertion 품질 린터 적용 전 더미 통과율은 18.5%였으나 적용 후 3.7%로 5배 개선.

## 5. 논문의 핵심 교훈

1. **현재 LLM은 소프트웨어 아키텍처 설계를 못 한다** — 단일 파일 모놀리식 구조로 도피하며, 함수를 적게 만들고 길게 쓴다
2. **태스크 난이도는 모델 무관하게 결정된다** — 소형 CLI 도구는 쉽고, FFmpeg/PHP 인터프리터는 모든 모델에게 어렵다
3. **인터넷 차단이 필수다** — LLM은 허용되면 반드시 소스를 찾아본다, 그리고 판사도 이를 탐지하기 어렵다
4. **더 많은 턴 = 더 좋은 결과가 아니다** — 턴 수와 성능의 Pearson 상관계수는 0.27에 불과하며, 모델별 스타일 차이일 뿐이다

### 향후 연구 방향 (논문 제안)

1. 멀티 에이전트 접근법 실험 — 현재는 단일 에이전트만 평가
2. Human-in-the-loop 시나리오 — 개발자가 설계 결정을 개입하는 방식
3. 비기능 요구사항 평가 추가 — 실행 속도, 메모리 사용량 등은 현재 미평가

## 6. 종합 평가

| 항목 | 판단 |
|------|------|
| 문제 제기 | 설득력 있음. "아키텍처 설계 능력"이라는 측면을 최초로 체계적으로 측정 |
| 벤치마크 설계 | 실용적. 소스 코드 불필요 → 언어/구조 무관 평가 가능, 확장 용이 |
| 실험 규모 | 9개 모델 × 200개 태스크 × 1,800회 실행으로 충분히 대규모 |
| 한계 | 비기능 요구사항(성능, 메모리) 미평가, 인간 기준선(human baseline) 없음 |
| 기존 벤치마크 대비 | SWE-bench는 "기존 코드 수정", ProgramBench는 "설계부터 구현" — 상호 보완적 |

### 핵심 한 줄 요약

> **"LLM은 코드를 작성할 수 있지만, 소프트웨어를 설계하지는 못한다"** — 모델이 생성한 코드는 동작하더라도 모놀리식이고 짧으며, 인간 개발자가 수년에 걸쳐 쌓은 모듈화된 아키텍처와는 근본적으로 다르다.
